## 2. `macros`

*"A dictionary of string substitutions. Global macros can be used in any configuration value; model macros are scoped to their model. Macro names must be <64 chars, match `^[a-zA-Z0-9_-]+$`, and not be `PID`, `PORT`, or `MODEL_ID`. Values can be string, number, or boolean. Macros can reference other macros defined before them."*

Three reserved names: `PID`, `PORT`, `MODEL_ID`.

## tool-swap notes

### 1. Read the shape before the keys

**One required key in the whole schema** (`models`), and one required key per model (`cmd`). Everything else — over a hundred keys across ten top-level blocks — has a default. That is guardrail 10 ([`13_OPEN_QUESTIONS.md`](../../13_OPEN_QUESTIONS.md) Part D) enforced by schema rather than by discipline, and it is the single most transferable thing here.

**Our config must additionally reject unknown keys.** llama-swap's schema uses `additionalProperties: false` on most nested blocks. [`00_CONTEXT_AND_MOTIVATION.md`](../../00_CONTEXT_AND_MOTIVATION.md) §2.6 records the R8 defect this prevents — `batch_size` written where `max_batch_size` was meant, silently ignored. Confirmation that the strictness in [`02_CONFIGURATION.md`](../../02_CONFIGURATION.md) is normal practice, not paranoia.

### 2. Keys we have an equivalent for

| llama-swap | tool-swap | Note |
| --- | --- | --- |
| `ttl`, `globalTTL` | `ttl` + `defaults.ttl` (**D9**) | Same semantics. Note their sentinel discipline: `-1` inherit, `0` never unload, `>0` enable. Ours should be equally explicit |
| `healthCheckTimeout` (120s) | cold-start bound (**D22** `queue_timeout`) | **Their default is 120s** — a useful reality check on ours |
| `checkEndpoint` | `/ready` | **Theirs is a path, ours is a contract.** See §3 below |
| `env` | per-tool `env` ([`02_CONFIGURATION.md`](../../02_CONFIGURATION.md)) | Same. Theirs is `NAME=value` strings; a mapping reads better |
| `macros` | `x-defaults` anchors + `${VAR:-default}` | [`02_CONFIGURATION.md`](../../02_CONFIGURATION.md) §1.6 cites this feature by name |
| `groups` | `groups` + `max_resident` (**D7**) | See §4 below |
| `hooks.on_startup.preload` | `keep_warm` | Same feature. Their note — *"define a group to prevent swapping"* when preloading several — is a trap we inherit verbatim |
| `logToStdout` | per-tool log files + `tswap logs` (**D8**) | Their `proxy`/`upstream`/`both`/`none` is a cleaner statement of the same choice |
| `unlisted` | — | Trivial to add to `/tools`; nobody has asked |
| `apiKeys` | bearer-token hook | [`README.md`](../../README.md) §5 non-goals leaves a hook. Theirs is a plain string array |
| `metadata` | `x-semantic` hints (**D13**) | Both are open-ended pass-through fields on the discovery response |
| `capabilities` | JSON Schema (**D13**) | **Ours is strictly stronger.** Theirs enumerates modality at the *model* level (`in: [text, image]`); ours types every input and output. This is the D13 thesis with a real comparison behind it |

### 3. `checkEndpoint` versus `/ready` — the difference that matters most

`checkEndpoint` defaults to `/health` and accepts any path or `none`. llama-swap polls it until the upstream answers, bounded by `healthCheckTimeout`.

**This is exactly the R8 defect that [`05_RUNTIME_AND_BATCHING.md`](../../05_RUNTIME_AND_BATCHING.md) §3.2 exists to correct** — readiness that reports *server-up*, not *weights-loaded*. For llama-swap it is not a defect, because `llama-server` does not answer until the GGUF is mapped. For an arbitrary Python server it is a coin flip, and for **our** tools it would be wrong nearly always: BentoML's `/readyz` answers before `load()` has run.

**Two conclusions.** First, `checkEndpoint` proves llama-swap's readiness model is *delegated* — the upstream defines what ready means. We cannot delegate, because we generate the server. Second, this is a genuine capability we have that they do not: **our `/ready` returns a reason on failure** ([`04_API_CONTRACT.md`](../../04_API_CONTRACT.md)), theirs is a poll for any 200.

### 4. `groups` versus ours, and the `matrix` we do not have

Their three booleans (`swap`, `exclusive`, `persistent`) express what ours expresses as a count (`max_resident`). Mostly equivalent: `swap: true` is `max_resident: 1`, `swap: false` is unbounded. But `exclusive` and `persistent` are **cross-group** relations we have no vocabulary for — *"this group's models must never be evicted by another group's"* is not expressible in [`06_LIFECYCLE_TTL_AND_SCHEDULING.md`](../../06_LIFECYCLE_TTL_AND_SCHEDULING.md).

**`matrix` is the more interesting object.** It is a constraint solver over declared legal combinations of concurrent models, and the line to read twice is:

> *"The solver minimizes eviction cost when swapping."*

with `evict_costs`: *"Relative cost of evicting a running model."*

**D25** says a request preempts an idle incumbent. It does not say *which* incumbent when several qualify, and [`06_LIFECYCLE_TTL_AND_SCHEDULING.md`](../../06_LIFECYCLE_TTL_AND_SCHEDULING.md) settles it with least-recently-used. `evict_costs` is the observation that LRU is the wrong metric when cold starts differ by an order of magnitude — evicting a tool with a 90-second load to make room for one with a 3-second load is a bad trade even if it was idle longer. **Our zoo has exactly that spread.** Raised as gap G2 in [`17_LLAMA_SWAP_PHILOSOPHY.md`](../../17_LLAMA_SWAP_PHILOSOPHY.md) §5.

Note the counterweight, and it is not small: `matrix` needs a DSL (`&`, `|`, `()`, `+ref`), a `vars` indirection table with 8-character names, and a solver. It is the clearest illustration in this capture of what **R4** costs when scheduling expressiveness wins.

### 5. `unloadTimeout` — a gap in our plan, cheaply filled

> *"Graceful timeout in seconds when unloading a model (manual, API, or TTL expiry) **before force-killing** the model process."*

Default 10s, globally and per-model. [ADR-0004](../../adr/0004-hard-stop-only-in-v1.md) makes hard stop our only reclamation path and **does not name a grace period**. `docker stop` defaults to SIGTERM then SIGKILL after 10 seconds — the same number, by coincidence or convergence — but we should say so rather than inherit it silently, because a tool mid-inference when its TTL fires is a real case and *"the OS reclaims"* is only true after the process actually dies. Raised as gap G1.

### 6. `concurrencyLimit` → 429

> *"Overrides allowed number of active parallel requests to a model. 0 uses internal default of 10. >0 overrides default. Requests exceeding limit get HTTP 429."*

**D22** gives us `max_queue_depth` and `queue_timeout` for requests arriving during a *cold start*. It says nothing about a tool that is `READY` but saturated. llama-swap has a per-model default of 10 in-flight and a 429 beyond it. Ours would interact with BentoML's own `threads=1` limiter and its `ServiceUnavailable("process is overloaded")` ([`../bentoml/health-endpoints-and-lifecycle-source.md`](../bentoml/health-endpoints-and-lifecycle-source.md)) — so the question is not only whether to have a limit, but which layer owns it and what the router does when the container says 503. Raised as gap G4.

### 7. `peers` — a growth path that is not Kubernetes

> *"A dictionary of remote peers and models they provide. Peers can be another llama-swap or any server that provides the /v1/ generative API endpoints…"*

Multi-host is a documented non-goal ([`README.md`](../../README.md) §5), with KServe named as the growth path ([`14_ALTERNATIVES_EVALUATION.md`](../../14_ALTERNATIVES_EVALUATION.md) §8). `peers` is a **third option nobody has considered**: static federation. A second GPU host runs its own tool-swap, and the first forwards tools it does not own, using the same proxy already built. No cluster, no scheduler rewrite, no control plane — and no cross-host scheduling either, which is exactly the feature that makes Kubernetes expensive.

Not a recommendation, and not in v1. Recorded because §8.6 of [`14_ALTERNATIVES_EVALUATION.md`](../../14_ALTERNATIVES_EVALUATION.md) names *"a second GPU host"* as a trigger for reconsidering Kubernetes, and this is evidence that the trigger has a cheaper answer worth pricing first.

### 8. Keys that exist only because they serve LLMs

`aliases`, `useModelName`, `includeAliasesInList`, `profiles`, `selectors`, `filters` (`stripParams`/`setParams`/`setParamsByID`), `sendLoadingState`, `compat.ignoreWebsockets`, `upstream.ignorePaths`, `capabilities`, and the whole `store`/`ui.activity` pair.

Every one traces to a single fact: **the model is named in the request body, and the request body is a chat completion.** Alias resolution, model-ID rewriting, sampling-parameter enforcement, streaming loading states in the `reasoning` field — none has meaning when the tool is named in the URL path and the body is a JSON-Schema-validated input object.

**This is D4's "behaviours, not surface" made countable: roughly a third of their schema evaporates under our API shape.** It is also the strongest available answer to *"why not just use llama-swap?"* — not that it lacks features, but that a third of its configuration surface would be dead weight, and the third we need most (typed I/O, batching, device assignment) is absent. Kept as supporting material for finding **F2** in [`INDEX.md`](INDEX.md) §3.
